# Required Payment-to-Email Flow

Use this workflow:

```text
Customer submits checkout
        ↓
Server validates course, fees, add-ons, customer details
        ↓
Square customer profile is found or created
        ↓
Square order is created
        ↓
Square payment is created
        ↓
Payment status becomes COMPLETED
        ↓
Booking/registration is stored or confirmed
        ↓
Customer confirmation email is sent
        ↓
Corsair notification email is sent
        ↓
Resend email IDs are stored

Resend webhooks update delivery status
```

```text

APPROVED
CANCELED
FAILED
```

do not send a misleading “payment completed” confirmation.

A Square `payment.updated` webhook is generated when payment fields such as status change, including completion. :contentReference[oaicite:1]{index=1}

# Required Square Customer Flow

Before creating a new customer:

1. Validate first name
2. Validate last name
3. Validate email
4. Validate phone
5. Normalize phone number
6. Search Square Customers using email, phone, or a stable internal reference
7. Reuse an exact existing customer where appropriate
8. Create a customer only if no suitable match exists
9. Store the returned Square customer ID
10. Pass that `customer_id` into CreatePayment
11. Associate the internal registration or booking ID using `reference_id`

Square recommends searching before creating a customer to avoid duplicate profiles. :contentReference[oaicite:3]{index=3}

## Customer fields

Use `company_name` only where relevant.

Do not use:

```text

Guest
Customer
Unknown

```

as replacement names.

If the customer refuses optional profile information, handle that honestly, but the checkout form should require the actual registration name needed for the class.

# Required Resend Webhook

Preferred production endpoint:

```text
https://www.corsairtacticalsolution.com/api/webhooks/resend
```

Use an existing equivalent endpoint if one already exists and is correct.

## Subscribe to these events

```text
email.sent
email.delivered
email.delivery_delayed
email.failed
email.bounced
email.complained
email.suppressed
```

Resend supports these delivery lifecycle events. `email.sent` means the API request succeeded and Resend will attempt delivery; `email.delivered` means the recipient mail server accepted the message. Failures, delays, bounces, complaints, and suppressions each have their own event. :contentReference[oaicite:6]{index=6}

Do not enable these unless specifically required:

```text
email.opened
email.clicked
email.received
contact.created
contact.updated
contact.deleted
domain.created
domain.updated
domain.deleted
```

`email.received` is for inbound email, not normal outgoing course confirmations.

# Production Versus Sandbox Decision

After the audit, classify the live state:

## GREEN

Use Production if:

- Correct Application ID
- Correct Location ID
- Correct access token
- Correct production SDK
- Correct totals
- Payments complete
- Customer profiles are linked
- Webhooks are working
- Confirmation emails are working

## YELLOW

Keep Production but temporarily disable affected courses if:

- Payment succeeds
- Amounts are correct
- Only email confirmation is failing
- Registration can be recovered from Square
- The issue is isolated

Provide a manual reconciliation report for affected payments.

## RED

Temporarily disable all live checkout if:

- Wrong account receives funds
- Wrong amounts are charged
- Duplicate charges occur
- Payments complete without an order or registration record
- Production uses Sandbox credentials
- Customer payment status cannot be trusted
- Webhook processing creates duplicate bookings
- The checkout is publicly accepting unusable payments

Do not replace the public live checkout with Sandbox.
