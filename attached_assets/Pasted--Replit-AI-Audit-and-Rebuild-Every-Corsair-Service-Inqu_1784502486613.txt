# Phase 1 — Audit the Existing Implementation Before Editing

Inspect every active service page and document what currently exists.

At minimum:

```text

/church-safety
/property-manager-services
/event-security
/private-investigations
/security-training
/realtor-safety-program
```

For each route, identify:

- Current hero CTA label and destination
- Current body CTA label and destination
- Whether a service-specific form exists
- Form anchor or modal identifier
- Current fields
- Current dropdowns
- Current API endpoint
- Submitted service ID
- Email subject behavior
- Whether the form actually appears in production
- Whether its buttons still point to Contact Me
- Whether its email is delivered

Do not assume the previous task was completed just because configuration files exist.

Inspect the rendered production behavior and the repository implementation.

## Required root-cause investigation

Determine whether the failure comes from:

- Service pages still using generic contact links
- A shared hero component with a `/contact` fallback
- CTA configuration not being passed to the page
- Form components created but never mounted
- Wrong anchor IDs
- Locale keys still containing contact routes
- Hash navigation being removed or ignored
- Modal triggers not connected
- A stale deployment
- Form endpoint rejecting service submissions
- A branch or repository mismatch

Report the root cause in the completion report.

# Form Design Standards

The forms should feel professional, modern, and easier to complete than the paper intake form.

Use clearly separated sections such as:

1. Contact Information
2. Organization or Location
3. Service Details
4. Current Conditions
5. Concerns and Goals
6. Acknowledgment

Use:

- Two-column layouts on desktop where appropriate
- One-column layouts on mobile
- Dropdowns for one-answer controlled choices
- Radio buttons for short yes/no/unsure choices
- Checkbox groups when multiple services may be selected
- Date fields for actual dates
- Time fields for actual start and end times
- Number inputs for quantities
- Textareas for detailed needs and concerns

Do not make every field a text box.

Do not make the initial form excessively long.

Use conditional fields to reveal additional questions only when relevant.

# Email System

Use the existing approved Corsair email provider and recipient configuration.

Do not create seven separate email endpoints unless the repository architecture requires it.

A shared secure endpoint is preferred.

## Server requirements

The server must:

- Validate `serviceId`
- Reject unsupported IDs with HTTP 400
- Generate the subject server-side
- Sanitize dynamic subject values
- Validate every submitted field
- Include every completed relevant field
- Exclude hidden and inapplicable fields
- Include source route
- Include submission time
- Include a submission ID
- Use the validated visitor email as reply-to where supported
- Produce a readable HTML and plain-text email
- Record delivery failure accurately

Do not accept an arbitrary browser-supplied subject.

- Required fields
- Email
- Phone
- ZIP Code

- Times
- Number ranges
- Dropdown values
