# Critical CTA Rule

On every service page, both service inquiry buttons must do one of the following:

## Preferred implementation

Scroll to one embedded form on the same page:

```text
#service-inquiry
```

Example:

```tsx
href="#service-inquiry"
```

or an accessible scroll handler.

## Acceptable implementation

Open one service-specific modal or drawer on the same page.

The modal must:

- Contain the correct form
- Be keyboard accessible
- Close with Escape
- Trap focus
- Return focus to the trigger
- Never route to Contact Me

# Forbidden CTA Destinations

No hero or body service-form button may point to:

```text

/contact-us

```

```tsx
router.push("/contact")

router.push("/contact-me")
```

Do not preserve fallback behavior that redirects to Contact Me when a form configuration is missing. Missing service configuration should be treated as an implementation error and fixed.

The general Contact Me page should remain available for general inquiries only.

```text

```

```ts
type ServiceInquiryConfig = {

  sourcePath: string;

  heroCtaLabel: string;

  submitLabel: string;
  fields: ServiceInquiryField[];
```

- source path

# Button Placement Requirements

Every service page must have exactly two prominent service-form CTAs.

## Hero CTA

Place inside the hero.

It must be visible and accessible on desktop and mobile.

## Body CTA

Place lower on the page after meaningful service content, such as:

- After benefits
- After process
- Before the closing statement
- Inside a closing CTA section

Do not place the body CTA immediately beside the hero CTA.

Both buttons must reach the same single form.

Do not render two copies of the form.

---

# Unique Form Requirement

A form is considered unique only when it has service-specific:

- Title
- Description
- Labels
- Field choices
- Service ID
- Email subject
- Email body
- Source route

Changing only a hidden service name on an otherwise generic Contact Me form is not enough.

The user should immediately see that the form belongs to the service page they are visiting.

# Email Delivery

Use the existing approved Corsair email infrastructure.

A shared endpoint is acceptable, but the endpoint must support service-specific submissions securely.

The server must:

- Validate `serviceId`
- Reject unknown service IDs with HTTP 400
- Generate subjects server-side
- Format submitted fields clearly
- Include the source page
- Include the service name
- Include submission time
- Include all completed fields
- Use the validated visitor email as reply-to where supported
- Send to the existing approved Corsair business recipient

Do not expose:

- recipient addresses
- API keys
- tokens
- SMTP passwords
- environment values

# Controlled Subject Mapping

Do not accept an arbitrary subject from the browser.

Use a server-controlled mapping such as:

```ts
const serviceSubjects = {
  securityAudits: "New Security Audit Request",
  churchSafety: "New Church Safety Services Request",
  propertySecurity: "New Property Security Services Request",
  eventSecurity: "New Event Security Request",
  privateInvestigations: "New Confidential Investigation Consultation",
  securityTraining: "New Security Training Information Request",
  realtorSafety: "New Realtor Safety Program Request",
} as const;
```

Dynamic values such as names, organizations, and dates may be appended only after validation and sanitization.
