3. Public Booking Is Now Required

Public booking is part of Corsair launch readiness.

Build or complete a reusable booking system that works through FSTS-WOS™.

Do not create a Corsair-only booking implementation.

The booking system must be reusable by future sites that offer:

- Courses
- Classes
- Events
- Appointments
- Training sessions

Public booking flow

A visitor should be able to:

1. Open a class/course/event on the Corsair website.
2. See current availability.
3. Select an available session.
4. Enter required customer information.
5. Accept required terms/waivers if configured.
6. Submit the booking.
7. Receive confirmation.
8. Have the registration appear immediately in the Corsair dashboard.

Support free booking first, with payment integration attached when a class requires payment.

5. Capacity Enforcement

Capacity must be authoritative and enforced server-side.

For each class/session support:

- Maximum capacity
- Confirmed registrations
- Seats remaining
- Nearly full threshold
- Full status
- Waitlist capacity
- Waitlist count
- Registration opening time
- Registration closing time

When capacity is reached:

- Close standard registration automatically.
- Change the public CTA to "Class Full".
- Prevent another registration from exceeding capacity.
- Open waitlist when enabled.
- Notify Corsair through the dashboard.

Use atomic backend enforcement so two customers cannot take the final seat simultaneously.

6. Waitlist

If enabled:

- Customer can join the waitlist.
- Waitlist order is preserved.
- Client sees the queue in the dashboard.
- Cancellation may promote the next eligible customer.
- Promotion updates capacity correctly.
- Promoted customer receives notification.
- Duplicate waitlist entries are prevented.

7. Booking Cancellation

Support authorized cancellation.

When a booking is cancelled:

- Registration status updates.
- Capacity is recalculated.
- Seat becomes available when appropriate.
- Waitlist promotion may occur.
- Customer receives cancellation confirmation.
- Client sees the updated status.

Preserve the registration record for reporting/audit purposes.

8. Class and Event Lifecycle Automation

The dashboard must automatically know when a class/event is:

- Draft
- Upcoming
- Registration Open
- Nearly Full
- Full
- Waitlist Open
- Registration Closed
- In Progress
- Completed
- Cancelled
- Archived

Use:

- Start date/time
- End date/time
- Timezone
- Registration dates
- Capacity
- Cancellation state

When a class/event passes its end time:

1. Close registration.
2. Mark it completed/past.
3. Remove it from Upcoming content.
4. Move it to Past Events or Past Classes.
5. Keep it available in the dashboard.
6. Preserve registrations and attendance records.
7. Expire/archive linked flyers where appropriate.

Do not require the client to manually move every completed event.

17. Payment Readiness

Payments are not required for every booking, but the booking architecture must support them.

For any paid Corsair class/event:

Booking → Price validation → Corsair merchant account → payment → webhook → registration → capacity → email.

Do not use FSTS platform billing credentials for Corsair customer transactions.

If Corsair has not supplied merchant credentials, free booking must still work and paid booking should clearly show as unavailable rather than failing unpredictably.
