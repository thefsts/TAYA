## The rule
Never regenerate `package-lock.json` locally (with npm 11+) and push to `thefsts/Corsair-Tactical-Solutions`.
Vercel's build npm resolves `@emnapi/*` and other native-addon transitive deps to different versions,
causing `npm ci EUSAGE` immediately.

**Why:** Discovered when adding vitest to devDeps without updating the lock file caused sub-13s
npm ci failures. Fixing the lock file locally (npm 11.6.2) introduced @emnapi resolution mismatches
with Vercel's npm, causing a different EUSAGE failure. The working fix was to restore the
lock file from the last green deployment that Vercel itself produced.

**How to apply:**
- When adding/removing deps in `package.json`, push ONLY `package.json` and change `installCommand`
  in `vercel.json` to `npm install` for the next deploy, then restore `npm ci` after the lock file
  is updated by Vercel's own build.
- OR: restore the most recent green lock file that Vercel produced, ensure package.json deps match,
  and push together.
- Never commit a lock file generated by a local npm install — only Vercel-generated lock files are safe.

## What the npm ci fast-fail symptoms look like
- Build fails in 9–13 seconds: package.json and package-lock.json are out of sync (added dep without updating lock)
- Build fails in <30s with EUSAGE `@emnapi/runtime@X missing from lock file`: locally-regenerated lock file
  has native-addon resolution mismatch with Vercel's npm version
- Build fails in ~80s with `npm error Exit handler never called!`: OOM/SIGKILL from large transitive dep install (e.g. vitest's 200+ packages)

## vitest in the Corsair repo
`vitest` was added to `package.json` devDeps but should NOT be there — the website build does not
need it. The `*.test.ts` and `vitest.config.ts` files remain in the repo for local dev use but are
excluded from tsconfig compilation. Tests must be run in a separate environment with vitest installed
ad-hoc (`npx vitest`), NOT as part of the `npm ci` / `next build` pipeline.
