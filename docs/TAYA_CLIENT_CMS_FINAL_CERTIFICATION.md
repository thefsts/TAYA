## 3. Defects discovered and fixed during this certification

A certification that finds nothing is usually a certification that looked at nothing. This audit found three genuine production defects. All three are now fixed, deployed, and verified live. None remain open.

### 3.1 Defect one — Convex production deployment drift (deploy-pipeline gap)

Described in section 2 above. Discovered while cross-checking the deployed backend function inventory against main during the early production-posture checks. Impact: the production UI could invoke functions that did not exist yet on the production backend, or receive stale behavior. Remediation: guarded production deploy executed; production Convex `uncommon-cobra-336` now serves 491 functions current with main. Verified live by function inventory and by subsequent end-to-end route checks. Residual risk accepted: Convex deploys remain manual by design (the fail-closed guard is intentional protection for production data); the runbook already documents that every merge touching `convex/` requires `bash scripts/deploy-convex.sh`.

### 3.2 Defect two — dead seed branding URLs (PR #20, commit `2cba337`, merged as `022053d`)

The Corsair seed configuration (`seedCorsair.ts`) pointed `logoUrl` and `faviconUrl` at an owner-side Google Cloud Storage bucket (`storage.googleapis.com/corsair-tactical/*`) whose entire contents return 404 — all 18 such URLs in the seed are dead because the owner-side bucket is offline. Client impact: the branded sign-in page silently fell back to the TAYA logo, and any surface relying on the seeded client logo would show nothing. The fix was made at the source of truth (the seed), not as a production data patch: `logoUrl` now points at the client's own live site asset `https://www.corsairtacticalsolution.com/corsair-logo-transparent.png` (verified live, natural width 1024) and `faviconUrl` at `https://www.corsairtacticalsolution.com/favicon.ico`. PR #20 passed CI (author identity check, quality suite, Vercel previews for both taya-system and taya-website), was merged with a true merge commit, the production Convex deployment was refreshed, and `seedBranding` was re-run against production (`{ok:true}`). Verified live afterward: the branded sign-in page at `/sign-in?site=corsair-tactical-solutions` renders the Corsair client logo at 64×64 top-center and the TAYA logo inside the Clerk card, both legible on the light background — the client's brand present, TAYA's identity retained. This is the exact behavior the locked scope requires.

### 3.3 Defect three — dead webhook host shown to clients (PR #21, commit `c8383c0`, merged as `3a4ec3e`)

Found by the dead-UI audit, which swept not just the main bundle but all 156 referenced asset chunks of the deployed production build — page components live in separate code-split chunks, and the main bundle alone would have missed this. The deployed production chunk `PaymentProviders-BETxOnGw.js` (23 KB) instructed clients, in the Payment Providers → Settings tab, to register their payment-provider webhooks at `https://clean-marlin-94.convex.cloud/api/payment/webhook` — a retired development deployment. The instruction was doubly wrong: the host was dead (verified live: 404), and even on a live deployment the `.convex.cloud` host returns 404 for HTTP routes because Convex HTTP actions are served from the deployment's `*.convex.site` host. Any client who followed the on-screen instruction would have registered a webhook that never fires, silently breaking payment event capture. Verified live during the audit: the correct production route `https://uncommon-cobra-336.convex.site/api/payment/webhook?provider=square&slug=corsair-tactical-solutions` rejects an unsigned POST with 401 (route live, signature enforcement working). The fix derives the base URL at runtime from `VITE_CONVEX_URL` via `.replace("convex.cloud", "convex.site")` — the exact established pattern already used by `ReviewsManager.tsx` (line 56) and `PublicForm` — so every environment (dev, preview, production) shows clients the URL that actually receives their webhooks, with a source comment forbidding hardcoded deployment URLs. Three regression tests were added in `src/test/payment-webhook-url.test.tsx`: the production URL renders correctly with no clean-marlin reference; a custom dev deployment URL is followed rather than any hardcoded production host; and the provider segment defaults to `square` when the active connector lacks a provider. The repo-wide sweep confirmed the hardcoded host had exactly one shipped occurrence; the e2e helper fallback and documentation mentions were verified out of scope and left untouched. PR #21 passed all checks (author identity, quality pass in 1m2s, Vercel taya-system and taya-website both green), was merged with a true merge commit to main `3a4ec3e`, and was verified live in production: the new deployed chunk `PaymentProviders-BAfkPmdH.js` contains zero clean-marlin references and renders the env-derived URL `${CONVEX_HTTP_URL}/api/payment/webhook?provider=${…}/slug=${…}`.

The apex of the plural domain 301-redirects, and its `www` host presents a TLS certificate mismatch. Recommended owner action: correct the DNS records to the singular domain or complete the redirect chain with valid TLS. Fourteen content images on the public site are dead links to owner-side hosting; they should be re-uploaded through the CMS Media Library, which is fully functional. The Resend transactional-email sender has a pending `fromEmail` domain verification on the owner's side; email sending will activate once the owner completes domain verification in Resend. Finally, the public site's own client-side fetches target the slug `corsair-tactical` against the retired `clean-marlin-94` Convex deployment, which 404s and therefore zeroes the public site's statistics widget. This is owner-side external infrastructure built outside this CMS scope; the TAYA dashboard side is fully functional against production, and the fix belongs to the owner's public-site deployment configuration.
